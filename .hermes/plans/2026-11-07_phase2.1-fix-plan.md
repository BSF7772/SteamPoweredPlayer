## 1. Findings (what is actually wrong)

### 1.1 Root cause of most clip bugs: the clip time axis
`SessionMedia.ChunkStartSeconds(n) = (n − 1) · 3 s` assumes chunk numbers are on the tfdt axis. That holds for cache sessions but **not
for clips**: `docs/steam-recording-format.md` (line ~59) already records that clips restart chunk numbers at 1 but keep the
session's **absolute tfdt** (chunk 1 of one clip starts at 585.0 s). With the lead EDL, mpv's `time-pos` is then the real tfdt
(e.g. 1536 s), while the UI origin is computed as 0, so:
- `25:36.6 / 0:12` in `TMP/2.png`: UI position = tfdt − 0, duration = 12 s → pointer and timestamp wrong.
- `+5 s` jumps to the end: the target is clamped against a 12 s duration on an axis where the position is already 1536 s.
- A-B loop broken on clips: A and B are stored on one axis and compared on the other.
- No markers on clips: marker offsets (field 1.5.10) are on the tfdt axis, the lane is drawn on the 0..12 s axis → all outside.
- Audio silent for a few seconds on clips: the lead EDL's first part is `N0·3 s` = 3 s for chunk 1, but the real tfdt is far
  larger. mpv sees a timestamp jump at the start and drops/realigns audio until it catches up. (Hypothesis; agent A verifies.)

**Fix direction:** the media origin must come from the **real tfdt of the first chunk on disk** (read from the first fragment's
`tfdt` box, already parsed by `FirstFragment`) and be stored in `SessionMedia` (e.g. `TfdtOriginSeconds`), with
`ChunkStartSeconds(n) = TfdtOrigin + (n − N0) · 3 s`. The lead EDL's first part becomes `TfdtOrigin + (N0−1)… ` stretched to match.
Cache sessions must give identical results to today (golden EDLs unchanged for them).

### 1.2 Markers missing on CS2 cache sessions too
The maintainer saw no markers at all, including CS2 (which emits kill/death markers). Either the same axis bug (clips) or
timelines are not loaded/matched for the session (cache). Agent A checks both with the real library and reports counts per
recording.

### 1.3 (Withdrawn) Game title in the player
The unexpected game name in the player header is correct: the maintainer renamed that game in Steam. The lookup is right; nothing to fix.

### 1.4 Crashes
- Player → `<` back from a saved clip crashes (`MainWindow.NavigateToLibrary` → `ContentFrame.GoBack()`); likely the Player page

- Settings → Library crashes. Same `Frame` navigation code in `MainWindow.xaml.cs`.
Both need the exception from `PlayerLog`/crash log first, then a test in `--uicheck` that reproduces them before the fix.

## 5. How the orchestrator watches the agents

**Launch**
- Wave 1: three `Agent` calls in one message, `isolation: "worktree"`, `run_in_background: true` (A, C, D). Fill `<REAL_LIBRARY>`
  from the local environment; add "D-TRICK approved" to C only if the maintainer approved it.
- Record each agent's id, worktree path and branch in the session (not in the repo).

**While they run (no polling loops; react to notifications)**
- Agents notify on completion. Between notifications, only when the maintainer asks or an agent has been silent for long,
  read its `.agent-progress.md` and `git -C <worktree> log --oneline main..HEAD`.
- Red flags → send a correction with `SendMessage` (same agent keeps its context): edits outside its owned files
  (`git -C <wt> diff --name-only main` vs §2), a test deleted/skipped/weakened, real paths or game names in a diff, a budget
  changed, a fix that catches an exception instead of removing its cause, `library.json` format change, writes under the
  Steam folder, a test taking > 60 s.
- An agent that reports "blocked" gets an answer or the question goes to the maintainer. Never guess the maintainer's decision.

**When an agent finishes (its report is a claim, not proof)**
1. Read the report; then read the full diff yourself (`git diff main...<branch>`).
2. Check ownership, SPDX headers, no personal data (`git diff | grep -iE "<lib path fragments>|steamapps|userdata"` with the
   real fragments kept outside the repo).
3. In the worktree: `dotnet build src -c Release`, `dotnet test tests`; once D is merged: `--realcheck`, `--uicheck`.
4. Not good enough → `SendMessage` with the exact failing evidence; don't fix it silently in the orchestrator unless it's a
   one-line merge glue.
5. Good → merge into `main` (`--no-ff`, message `Merge Phase 2.1: <agent scope>`), re-run `dotnet test` on main, push per
   AGENTS.md.

**Merge order:** D → A → C → (wave 2) B → (wave 3) R findings. Conflicts in shared seams (MainWindow, AutomationIds) are resolved
by the orchestrator.

**After wave 2:** run `--realcheck` and `--uicheck`, collect the window captures, send them to the maintainer with
`SendUserFile` (they show real games, so they stay out of the repo), plus a checklist of F1–F13 with PASS/FAIL. Update the main
plan's §9 (Phase 2.1 results; RAM decision D-RAM recorded as final) and AGENTS.md status line.

**Gate:** the maintainer re-tests. Phase 2 is PASSED only on their word; Phase 3 is not proposed before that.
